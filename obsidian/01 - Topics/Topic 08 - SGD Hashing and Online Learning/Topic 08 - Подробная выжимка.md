# Topic 08 — SGD, Hashing и Online Learning: подробная выжимка

[[ML Course]] · [[Topic 07 - Подробная выжимка]]

## 1. Главная идея

До этой темы я мысленно мог представить обучение так:

```text
весь train dataset → model.fit(...) → готовая модель
```

Но что если dataset огромный, постоянно растёт или распределение меняется каждый час?

Тогда полезна другая схема:

```text
batch 1 → обновили модель
batch 2 → обновили ту же модель
batch 3 → обновили ту же модель
...
```

Это online / incremental learning.

## 2. Batch learning vs online learning

### Batch

Модель периодически обучается на фиксированном наборе данных.

Плюсы:

- проще воспроизводить;
- проще валидировать;
- можно использовать сложные batch-алгоритмы.

Минусы:

- нужно хранить/перечитывать данные;
- дорого при огромном dataset;
- модель обновляется не сразу.

### Online

Параметры обновляются по одному объекту или небольшому mini-batch.

Плюсы:

- ограниченная память;
- быстрое обновление;
- подходит для потоков.

Минусы:

- чувствительность к порядку данных;
- сложнее monitoring;
- drift может незаметно испортить модель;
- сложнее воспроизводить точное состояние.

## 3. Откуда берётся Gradient Descent

Есть параметры модели `w` и функция потерь `L(w)`.

Хотим уменьшить loss. Градиент показывает направление роста, поэтому идём в противоположную сторону:

```text
w_new = w_old - η * gradient
```

`η` — learning rate.

Если шаг слишком большой — можем перескакивать минимум. Слишком маленький — обучение будет очень медленным.

## 4. Batch Gradient Descent

Градиент считается по всему train dataset перед одним обновлением.

Плюс — направление стабильное. Минус — каждый шаг дорогой.

Для миллионов объектов это может быть непрактично.

## 5. Stochastic Gradient Descent

SGD оценивает градиент по одному объекту или mini-batch.

```text
объект → gradient → update
объект → gradient → update
...
```

Градиент шумный, но обновления дешёвые и частые.

Этот шум не обязательно плох: он иногда помогает не застревать в неудачных областях оптимизации.

## 6. Epoch

Одна epoch — примерно один полный проход по train data.

Если dataset имеет миллион строк и batch size = 1000, одна epoch содержит примерно 1000 updates.

Важно различать:

```text
iteration/update ≠ epoch
```

## 7. Learning rate

Это один из ключевых параметров SGD.

Слишком большой:

```text
loss скачет / расходится
```

Слишком маленький:

```text
loss уменьшается очень медленно
```

Часто learning rate постепенно уменьшают по мере обучения.

Интуиция:

```text
в начале → крупные шаги, быстро ищем хорошую область
позже → маленькие шаги, аккуратно уточняем параметры
```

## 8. Почему scaling важен

SGD оптимизирует параметры численно. Признаки совершенно разных масштабов создают неудобную геометрию loss surface и могут сильно замедлить оптимизацию.

Поэтому для линейных SGD-моделей scaling обычно важен.

Но в настоящем online режиме обычный `StandardScaler.fit()` по будущим данным невозможен. Нужен либо заранее фиксированный preprocessing, либо incremental statistics (`partial_fit`).

## 9. `SGDClassifier`

Пример:

```python
from sklearn.linear_model import SGDClassifier

model = SGDClassifier(
    loss="log_loss",
    penalty="l2",
    random_state=42,
)
```

`loss="log_loss"` делает модель близкой по смыслу к logistic regression, но оптимизируемой через SGD.

## 10. `partial_fit`

Ключевой метод incremental learning:

```python
classes = np.array([0, 1])

for X_batch, y_batch in stream:
    model.partial_fit(X_batch, y_batch, classes=classes)
```

При первом вызове для классификации обычно нужно передать возможные классы.

В отличие от повторного `.fit()`, `partial_fit()` продолжает обновлять существующее состояние модели.

## 11. Но pipeline тоже должен быть online-compatible

Ошибка мышления:

> Раз модель имеет `partial_fit`, значит весь ML pipeline стал online.

Нет.

Если перед моделью стоит encoder/scaler, который требует полного `fit`, он может стать bottleneck или источником leakage.

Нужно проверять incremental-совместимость каждого stateful шага.

## 12. Feature Hashing

При обычном one-hot нужен vocabulary:

```text
слово/категория → конкретный индекс столбца
```

Vocabulary может стать огромным и должен храниться.

Hashing trick делает иначе:

```text
feature name → hash → индекс от 0 до N-1
```

Размер пространства фиксируется заранее.

```python
from sklearn.feature_extraction import FeatureHasher

hasher = FeatureHasher(n_features=2**18, input_type="dict")
```

## 13. Почему hashing удобен для потока

- не нужно сначала собирать vocabulary;
- unseen category обрабатывается естественно;
- память ограничена `n_features`;
- одинаковая hash-функция даёт одинаковую координату в train и production.

Это особенно полезно для текста, рекламы, логов, high-cardinality категорий.

## 14. Hash collisions

Две разные категории могут попасть в одну координату.

Это цена фиксированной памяти.

```text
feature_A → bucket 125
feature_B → bucket 125
```

Если `n_features` достаточно велико, умеренные collisions часто допустимы.

Но интерпретация коэффициентов становится намного сложнее: координата уже не обязательно соответствует одному понятному признаку.

## 15. Vowpal Wabbit — что важно понять

В рамках курса важнее не синтаксис конкретной команды VW, а архитектурная идея:

```text
streaming input
+ feature hashing
+ быстрый online optimizer
+ ограниченная память
```

То есть можно учиться на данных, которые намного больше RAM.

Это исторически важный пример engineering-oriented ML.

## 16. Online validation

Случайный KFold для настоящего потока часто не отражает production.

Более естественная схема — prequential evaluation:

```text
пришёл объект
↓
сначала prediction
↓
когда известен label — измерили ошибку
↓
после этого обновили модель
```

То есть модель сначала экзаменуется на новом объекте и только потом имеет право на нём учиться.

## 17. Concept drift

Мир меняется.

Примеры:

- пользователи меняют поведение;
- появляется новый тип fraud;
- сезон меняет спрос;
- рекламная площадка меняет интерфейс;
- экономический кризис меняет распределения.

Если зависимость `X → y` изменилась, старая модель может постепенно деградировать.

Это concept drift.

## 18. Data drift vs concept drift

### Data drift

Изменилось распределение `X`.

```text
P(X) changed
```

### Concept drift

Изменилась связь признаков с target.

```text
P(y | X) changed
```

Первое не всегда означает ухудшение модели, второе непосредственно угрожает predictive quality.

## 19. Monitoring

Online model без monitoring опасен.

Нужно отслеживать:

- метрики во времени;
- distribution признаков;
- долю классов;
- delayed labels;
- количество unseen/аномальных значений;
- скорость обновлений;
- стабильность loss;
- бизнес-метрику.

Средняя accuracy за весь год может скрыть, что последние две недели модель уже плохая.

## 20. Feedback loops

Особенно опасный случай: prediction модели меняет мир, из которого потом приходят новые данные.

Например:

```text
модель решила не показывать рекламу пользователю
↓
мы не увидели, кликнул бы он или нет
↓
новые labels зависят от старой модели
```

Это feedback loop. Данные перестают быть нейтральным наблюдением среды.

## 21. Когда online learning действительно нужен

Не нужно делать streaming просто потому, что это звучит технологично.

Online подход оправдан, если:

- dataset не помещается в память;
- данные приходят постоянно;
- модель должна быстро адаптироваться;
- full retrain слишком дорог;
- high-cardinality пространство удобно hashing-представлением.

Если dataset небольшой и обновляется раз в месяц, обычный batch pipeline часто проще и надёжнее.

## 22. Типичные ошибки

- использовать `partial_fit`, но забыть про preprocessing;
- не перемешивать данные там, где порядок не имеет смысла;
- случайно перемешивать временной поток там, где порядок как раз критичен;
- не контролировать learning rate;
- считать collisions ошибкой реализации hashing;
- не мониторить качество во времени;
- обновлять модель на labels, которые приходят с большой задержкой, не учитывая это;
- автоматически учиться на каждом новом объекте без защиты от аномалий/атаки/сбоев.
